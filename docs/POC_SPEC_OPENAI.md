# iOS AI 动画相机 — Core ML 实时神经风格迁移 POC 需求

（用户 2026-10-29 提供，注明为 OpenAI 所写的需求稿。注：其中 Phase 1 后等待确认的流程已被用户本人取消——由 Sunny 代为决策，直接实施；真机测试由用户本人执行，Sunny 侧用模拟器环境完成验证。技术要求与诚实性标准仍然有效。）

## 一、项目背景

当前 iOS App 已经完成真机验证，具备以下能力：

- iPhone 摄像头实时取景。
- 中文 UI。
- 三种动画风格切换：手绘治愈风、Q版萌系、2.5D 动画风。
- 视频录制与保存。
- 基于 Metal 着色器的实时画面处理。
- 工程中已预留 Core ML 模型集成位置。

目前三个风格实际采用 Metal Shader 近似实现，通过描边、色彩量化等方式模拟动画效果。

实际视觉效果明显不符合产品预期，主要问题包括：

1. 画面仍然具有明显的滤镜感，缺乏真正的动画重绘效果。
2. 地板、天花板等平坦区域出现噪点和斑点。
3. 整体色彩偏暗。
4. 部分风格描边过粗，呈现美式漫画特征，而不是自然、柔和的日系动画视觉效果。

经过评估，决定停止继续优化现有 Metal 滤镜作为核心动画化方案，转而验证真正的 Core ML 神经网络风格迁移。

## 二、本次任务目标

**本次任务只验证一个风格：手绘治愈风。**

目标是在 iPhone 上通过 Core ML 加载真正的神经网络图像风格迁移模型，将摄像头采集到的真实画面持续转换成接近日系手绘动画的效果，并实时显示。

要求：

- 必须使用真实的神经网络模型进行图像风格转换。
- 必须在 iPhone 本地运行，不依赖云端推理。
- 优先追求画面质量和视觉表现。
- 在画质可接受的基础上，优化帧率和延迟。
- 不得使用 Metal 滤镜冒充 AI 模型效果。
- 不得为了提高 FPS 而显著降低视觉质量。
- 保持现有 App 的主要功能和工程结构。

本次 POC 的核心问题只有一个：

**真正的端侧神经风格迁移，能否在真实 iPhone 摄像头画面中达到令人满意的日系手绘动画效果？**

本次不要求完成三个风格，不要求上线商业版本，也不要求训练新模型。

## 三、技术方案

### 3.1 模型选择

优先评估 AnimeGANv3 Hayao Core ML 模型，但不得未经核实就认定它是唯一或最佳方案。

要求：

1. 核查模型来源、版本、权重、许可证和使用限制。
2. 核实是否存在官方 Core ML 模型，以及是否能在当前 iOS 工程中正常运行。
3. 核查实际模型输入尺寸、输出尺寸、数据格式及归一化要求。
4. 如官方 Core ML 模型可用，优先使用官方模型。
5. 如果需要自行转换模型，必须记录转换方式、依赖版本及精度验证结果。
6. 如果 AnimeGANv3 效果不足，可以再评估其他轻量神经风格迁移模型，但不得无依据地更换或引入大量依赖。

必须明确区分模型代码许可证、预训练权重许可证、训练数据限制和商业使用权限。

对于授权不明确或明确禁止商业使用的模型：

- 不得直接作为可商用模型交付。
- 只有确认当前 POC 的具体使用方式符合许可证后，才可以集成测试。
- 无法确认授权时，先停止该模型的集成并报告，不得自行假定个人真机测试就必然合法。
- 不得通过第三方重新上传的权重或许可证标记绕开原始授权限制。

### 3.2 实时处理链路

目标架构：

iPhone Camera（AVFoundation）→ 视频帧采集 → 输入预处理 → Core ML 神经网络推理 → 输出图像后处理（必要时使用 Metal）→ 实时屏幕预览 → 视频录制与保存

具体要求：

- 复用现有 AVFoundation 摄像头采集流程。
- 复用现有 Core ML 预留架构。
- 模型只加载必要次数，不能每一帧重新初始化。
- 推理过程不得阻塞 UI 主线程。
- 使用有界帧队列或最新帧处理策略，避免推理积压导致预览延迟不断增长。
- 正确处理摄像头方向、镜像、裁剪、图像比例和颜色空间。
- 避免不必要的 CPU/GPU 数据复制。
- 在设备兼容的前提下，评估 Core ML 可用的 Neural Engine/GPU/CPU 计算配置。
- Metal 可以继续承担渲染、必要的色彩处理和性能优化，但不得成为主要风格转换实现。
- 保持现有拍摄、录制和保存功能。

### 3.3 画质要求

画质是本次 POC 的首要评价指标。

希望呈现以下特征：

- 明亮、自然、温暖的日系动画色彩。
- 柔和、清晰的轮廓线。
- 天空、建筑、树木、人物等呈现明显的动画风格。
- 平坦区域干净，不出现明显随机斑点。
- 保留人物和场景的主要结构。
- 人脸不发生严重畸变。
- 不出现明显的色块破碎和异常纹理。
- 摄像头移动时，画面尽可能保持稳定。
- 不出现严重的帧间闪烁或色彩跳变。

不得仅凭模型成功运行、画面出现颜色变化，就认定画质验收通过。

需要明确区分：

1. 模型成功集成。
2. 实时处理链路成功。
3. 动画化画质达到产品预期。

三个目标分别验收。

### 3.4 分辨率与性能

不要预设 30 FPS 是必须立即达到的硬性条件。

先对模型的实际画质进行评估，再针对性能优化。

至少测试模型支持的合理输入尺寸，并在具备模型支持和实际可执行性的前提下评估不同分辨率。

记录：

- 实际输入分辨率。
- 实际输出分辨率。
- AI 推理耗时（P50 / P95）。
- 预处理与后处理耗时。
- 实际输出 FPS。
- 端到端预览延迟（如果无法准确测量，需要说明测量方法和限制）。
- 内存使用。
- 设备温度及系统热状态。
- 连续运行期间的性能变化。
- 是否有丢帧、积压或明显卡顿。

参考性能目标：

- 优先争取 24–30 FPS。
- 如实际只能达到 10–15 FPS，也允许保留真实结果用于画质验证。
- 不得通过重复展示旧帧、伪造 FPS 等方式使性能指标看起来更好。
- 所有性能结论必须以实际设备测试数据为依据。

如果高质量模型无法实时运行，应明确报告性能瓶颈，而不是擅自退回 Metal 近似滤镜并宣称完成任务。

## 四、录制与保存

必须检查当前视频录制模块是否可以正确处理 Core ML 风格转换后的画面。

要求：

1. 实时预览显示 AI 风格转换结果。
2. 录制功能可以正常启动和停止。
3. 明确确认最终保存的视频是否包含 AI 风格化结果。
4. 保持正确的画面方向、宽高比例、时间戳和音视频同步。
5. 模型处理速度不足时，不能通过简单重复视频帧而隐瞒问题。
6. 如果现有录制架构无法直接支持 AI 输出，应先说明需要的修改，不要大规模重构。

如果由于模型帧率或编码链路限制，暂时无法稳定保存 AI 风格视频，可以将视频录制标记为未通过，但不得将原始视频冒充 AI 处理结果。

## 五、工程实现原则

本次任务采用最小侵入式改造。

必须遵循：

- 先阅读现有工程及相关代码，再提出实施方案。
- 尽可能复用已有 Core ML 接口和处理管线。
- 不重新设计整个摄像头模块。
- 不重写现有 UI。
- 不引入无关功能。
- 不为单一 POC 建立过度复杂的抽象层。
- 不添加不必要的兼容代码、重复逻辑或多套并行实现。
- 保留现有 Metal 处理能力作为独立技术模块，但不能作为 Core ML POC 的成功替代。
- 所有核心错误必须显式处理。
- 模型加载失败、推理失败、设备资源不足时，必须有可识别的错误状态。
- 禁止静默降级后仍显示 AI 模式正在运行。
- 不得修改现有无关业务功能。

依赖管理要求：

- 优先使用已有 Apple 官方框架。
- 不为简单的模型调用引入不必要的第三方库。
- 如需要 Python、PyTorch、coremltools 等转换依赖，应使用独立环境并固定版本。
- 检查版本兼容性和模型转换结果。
- 遇到依赖冲突、模型转换异常或精度显著偏差时停止并报告，不得强行升级或降级现有工程依赖。
- 不得修改全局 Python 环境或破坏当前可运行的 iOS 构建环境。

## 六、实施流程

### Phase 1：现状审查与方案确认

检查现有摄像头采集、Metal 渲染、Core ML 预留接口的实现；当前三个风格的处理链路；预览、录制和视频保存之间的关系；目标 iPhone 设备、iOS 版本及部署环境；可使用的神经风格迁移模型、授权情况和集成条件。

输出简洁的实施 Plan，包含：需要修改的文件、模型来源及许可证、处理链路设计、可能的性能瓶颈、测试方法、风险和停止条件。

（流程注记：用户已取消「等待确认」环节，由 Sunny 审查决策，实施方直接推进。）

### Phase 2：单模型集成

按照批准的 Plan：集成真实的 Core ML 模型；连接摄像头视频帧；完成必要的预处理与后处理；实现模型推理和实时预览；显示实际模型运行状态；不修改其他两个风格（流程注记：用户最新指令为「用 Core ML 替换现在的 Metal」，三槽位均以真模型为目标，无可信模型的槽位如实报告）；不改变现有 UI 结构，除非完成最基本的模式区分确有必要。

### Phase 3：真机测试

使用真实 iPhone 对以下场景测试：室内平坦区域（地板、天花板、墙面）；户外（建筑、天空、树木）；人物（人脸、头发、衣服）；运动（缓慢移动、快速转动摄像头）。需要保存原始画面与 AI 处理后的对应样本。检查视频稳定性、图像质量和性能指标。如没有可用真机测试通道，必须明确报告当前无法验证的项目，不得以模拟器测试替代真机验收。

（执行注记：真机测试由用户本人在 iPhone 14 Pro 上执行；Sunny 侧完成实现与模拟器环境验证，并提供真机测试清单。）

### Phase 4：验证报告

输出一份简洁报告，至少包括：

1. 使用的模型名称、版本及来源。
2. 模型使用许可与商业化限制。
3. 实际修改的文件。
4. Core ML 推理是否真正运行。
5. 实际输入及输出分辨率。
6. 实际 FPS 和推理延迟。
7. 视觉效果及存在的问题。
8. 视频录制和保存是否正常。
9. 当前是否可以离线使用。
10. 是否满足本次 POC 验收标准。
11. 是否建议继续采用该模型。
12. 如果不推荐，说明主要原因及下一步替代方向。

不得将未测试项目标记为通过。

## 七、验收标准

### P0 — 必须实现

- [ ] 真正的 Core ML 神经网络模型完成集成。
- [ ] 模型在真实 iPhone 上成功加载和推理。
- [ ] 摄像头画面经过真实 AI 风格转换。
- [ ] 能在 App 中持续显示处理后的实时画面。
- [ ] 不依赖云端 API。
- [ ] 不通过 Metal 滤镜伪装 AI 效果。
- [ ] 现有 App 基本功能未被破坏。
- [ ] 模型使用方式符合已确认的授权条件。

### P1 — 优先验证

- [ ] 明显优于当前 Metal 动画滤镜。
- [ ] 画面具有可辨识的日系手绘动画特征。
- [ ] 人物和场景结构基本稳定。
- [ ] 无严重噪点、闪烁或图像畸变。
- [ ] FPS、推理延迟和内存指标有真实记录。

### P2 — 后续优化

- [ ] 在画质可接受的前提下争取稳定 24–30 FPS。
- [ ] 优化时序一致性与动态场景表现。
- [ ] 进一步改善分辨率与图像细节。
- [ ] 研究第二、第三种风格的独立模型。
- [ ] 研究正式商业化许可或可商用模型替代。

## 八、停止条件

出现以下情况必须暂停相应阶段并报告：

1. 模型来源或授权无法确认。
2. Core ML 模型无法正常加载，且没有经过验证的兼容解决方法。
3. 模型转换后输出异常，或与原始模型效果明显不一致。
4. 需要对现有摄像头或录制架构进行重大重构。
5. 出现可能破坏现有构建环境的依赖冲突。
6. 实际设备性能严重不足，无法支持有意义的实时预览验证。
7. 模型效果明显无法满足基本的动画化目标。

不得为了形式上完成任务，而通过大量复杂代码、伪造运行状态、降级为 Metal 滤镜或者绕过错误处理来继续实施。

## 九、最终要求

这次 POC 不是为了证明 Core ML 能运行，而是为了验证：

**使用真正的端侧 AI 神经网络，能否让真实 iPhone 摄像头画面呈现明显优于现有滤镜的日系手绘动画效果。**

决策优先级：**画质 > 视频稳定性 > 实时性能 > 工程复杂度。**

但必须保证工程实现正确、可维护、可验证。

不要擅自进行大范围重构，不要接入收费云端服务。

最终以真实设备、真实模型输出及客观测试结果作为判断依据，而不是以代码完成度作为成功标准。
